# 任务路由与模式选择

本文件用于帮助 Agent 判断何时直接写作、何时追问、何时调用范文大纲、何时搜索、何时进入严格流程，以及最终交付什么形态的产物。

## 一、先识别任务类型

1. 起草：用户要求写、起草、撰写、生成某类公文或材料。
2. 润色改写：用户提供已有文本，要求优化、压缩、扩写、改成正式公文。
2b. 多轮改稿：用户基于本 Skill 已交付的产物提修改意见（结构或表达调整），按 `reference/revision_workflow.md` 执行。
3. 审查把关：用户要求检查格式、逻辑、政策依据、语言或风险。
4. 搜索支撑：用户要求找政策、依据、数据、案例。
5. 正式交付：用户明确要求 `.docx`、红头文件或正式排版文件（直接触发 Word）。

## 二、交付物形态：两个独立开关

任何写作任务，判断两件**互不影响**的事：

- **开关 A「是否命中正式公文范式」** → 决定**要不要 Word**。
- **开关 B「是否执行过深知搜索」** → 决定**要不要产出物 HTML**。

### 开关 A：公文范式清单（命中 → 出 Word）

**法定公文 15 种**：决议、决定、命令（令）、公报、公告、通告、意见、通知、通报、报告、请示、批复、议案、函、纪要。

- 对应文种标准：`01_report`、`02_qingshi`、`03_pifu`、`04_tongzhi`、`05_yijian`、`06_han`、`07_minutes`、`08_tongbao`、`09_tonggao`、`10_gonggao`、`16_decision`、`17_resolution`、`18_order`、`19_gazette`、`20_motion`。
- **视同公文**（按"函"处理，一并出 Word）：`11_fuhan_approve`、`12_fuhan_objection`（复函）、`13_reminder`（提醒函）。
- **不算公文**（走产出物 HTML）：`14_generic`、`15_business_docs`、`21_explanation`、`22_application`、`23_publicity`、`24_procurement`、`25_plan`、`26_summary`、`27_speech`、`28_rules`、`29_research`、`30_feasibility`、`31_review_material`、`32_ai_compute`。

判定用**文种硬匹配**（按上表，不靠模型自由裁量）。**例外优先**：用户明确要求 Word、红头、正式文件或套红头时，一律出 Word——但这**不压制**产出物 HTML。

### 开关 B：产出物 HTML（用过搜索就产出）

只要本任务执行过深知搜索（`scripts/deep_query.py` 深度/可信搜索，或 `scripts/dkag_search.py`），就生成 **1 个产出物 HTML**：单文件、顶部切换三页。

1. **正文页**：干净正式内容（与 Word 正文一致，不带任何角标、素材清单、知识专库链接；核验内容归第 2 页）。
2. **溯源核验报告页**：过程回顾 + 五项核验单 + 带 `[n]` 角标的正文（角标为可点击引文胶囊）。
3. **知识专库页**：检索命中的来源材料分组视图（内嵌分组 + 原文/专库外链）。

- 文件名按用户需求（正文标题）确定，形如 `XXX.html`。
- **未执行搜索的任务不产出该 HTML。**
- 该 HTML 由 `scripts/source_note_html.py` 从溯源 JSON 生成；原独立的"溯源核验报告 HTML"形态由其三页版本取代，不再单独产出。

### 交付矩阵

|  | 用过搜索 | 没用搜索 |
|---|---|---|
| **命中公文范式** | **Word ＋ 产出物 HTML** | **仅 Word** |
| **非公文** | **产出物 HTML** → 交付后问是否另出 Word | 按原流程（沿用现状，本矩阵不改动） |

### 非公文 + 用过搜索：交付后补 Word

交付产出物 HTML 时附**一句话**询问是否需要另出一份 Word（不制造多轮确认）。用户要，则用同一份正文调用 `scripts/format_document.py` 生成 `.docx`，不重复检索、不重写正文。

## 三、再判断复杂度

简单任务：

- 会议通知、时间地点变更、内部事务通知
- 简短告知函、提醒函
- 用户信息完整、无需政策依据

处理方式：读取必要文种标准后直接完成。交付形态按第二节两个开关判定（公文→Word；用过搜索→另出产出物 HTML）。只有用户明确说"直接在对话里给正文""不要生成文件""先看文字草稿"时，才在对话中输出正文。不要制造多轮确认。

常规任务：

- 通知、函、短报告、普通会议纪要
- 用户给出主题、对象、事项和基本要求

处理方式：必要时追问 1-3 个关键缺失信息。交付形态按两个开关判定；不先在聊天中发送正文初稿；只有用户明确要求对话输出正文时才例外。

复杂任务：

- 请示、复函、政策依据型报告
- 调研报告、实施方案、管理办法、工作总结、汇报材料
- 产业研究总结、产业发展报告、政策研究报告、年度发展总结
- 工作要点、专项整治方案、会议讲话、研讨发言等长篇材料
- 涉及政策、数据、案例或多章节结构

处理方式：优先调用公文范文大纲接口，返回可用大纲时先确认"大纲 + 搜索建议"；确认后按需进入搜索、素材确认和审查；交付形态按两个开关判定（此类任务通常都会执行搜索，因而都会产出产出物 HTML）。

高风险任务：

- 引用政策依据
- 回复来函、作出承诺或表达正式意见
- 涉及跨地区政策适用、数据真实性、红头文件

处理方式：必须执行素材来源检查和生成前审查。

## 四、五种模式如何组合

Tool Wrapper：

- 公文范文大纲脚本
- 深知搜索脚本
- Word 排版脚本
- 红头生成脚本
- 产出物 HTML 生成脚本（正文 / 溯源核验报告 / 知识专库 三页）

Generator：

- 默认写作模式
- 使用文种标准、用户材料和 `reference/material_usage_guidance.md` 生成内部正文草稿；长篇正式材料不得把草稿直接发给用户
- 对工作总结、工作要点、实施方案、专项整治方案、会议讲话、研讨发言、汇报材料等长篇材料，生成前先内部完成文体判断、结构选择、小标题策略和段落功能分配
- 可参考 `reference/standards/99_expressions.md`，但不得把参考句式机械套用成固定模板；长篇材料应先保证任务闭环，再考虑表达增强
- 对执行过搜索的任务，正式正文（Word 正文、产出物 HTML 的正文页）不得包含素材清单、知识专库链接或 URL；可点击溯源统一由产出物 HTML 承载

Reviewer：

- 生成前检查
- 生成后自检
- 用户要求"帮我看看有没有问题"时优先使用

Inversion：

- 需求不完整且无法合理推断时
- 长篇复杂材料开始前
- 一次最多问 3 个关键问题

Pipeline：

- 范文大纲返回可用结果并需要用户确认
- 执行过搜索的复杂公文
- 政策依据型材料
- 红头文件生成
- 需要用户确认素材或大纲的任务

## 五、决策规则

- 能直接完成的简单任务，直接完成。
- 信息缺失但可合理假设，先写并标注假设，不要频繁打断。
- 信息缺失会影响公文方向、对象、结论或风险时，先追问。
- 正式写作需求进入搜索前，先取范文大纲，统一调用 `scripts/outline_reference.py`（需 API Key；MCP 通道当前未启用）。返回可用大纲时，先让用户确认建议大纲和搜索建议。
- 范文大纲工具/接口失败、超时或返回无可用大纲时，不中断任务，不生成替代大纲，不进入大纲确认，直接按原流程继续。
- 需要政策、数据、案例支撑时，遵循 `reference/search_policy.md`，先展示搜索方案并等待用户确认。
- 短公文没有明确依据需求时，默认不做大规模检索；调研报告、政策研究报告和产业研究报告才使用较完整的政策、数据、案例检索。
- 用户确认搜索方案后，只能走深知脚本通道，**两阶段**：阶段一用 `scripts/deep_query.py`（返回经 `scripts/deep_convert.py` 转换），阶段二补搜用 `scripts/dkag_search.py`；全程不混用其他通道。不得使用 Web Search、Web Fetch、浏览器搜索或公开网页抓取替代。
- 深知搜索异常、空结果或素材不足时，先暂停请用户确认下一步，不得自行切换外部搜索。
- 搜索返回 `quota_exhausted=true`（积分/余额用尽）时禁止任何重试，立即引导用户到 MaaS 平台 `https://platform.dknowc.cn/auth/#/login` 实名认证再领积分或充值；未确认处理前不再调用搜索。
- **交付形态按第二节两个开关判定**：命中公文范式 → 生成 `.docx`；执行过搜索 → 生成产出物 HTML（`XXX.html`，三页）。两者可同时成立。如生成临时 Markdown 草稿，必须直接继续生成最终产物，不得先把正文或 `.md` 发给用户。
- 只有用户明确要求红头文件、红头版、套红头或生成红头时，才在普通 Word 基础上调用红头脚本。
- 用户基于已交付产物提修改意见时进入改稿轮：**底稿以最新产物为准**——有 Word 时以最新版 Word 为底稿；非公文只有产出物 HTML 时，以该 HTML 的正文页（对应内部正文 Markdown）为底稿。逐条落实用户意见并汇报，默认复用已有搜索结果不重复检索；详见 `reference/revision_workflow.md`。

## 六、交付路径

### 路径 A：公文范式（命中开关 A）

1. 确认必要信息。
2. 检索个人素材库并应用写作偏好（规则见 SKILL.md"个人素材库与写作偏好"）。
3. 优先调用公文范文大纲接口；返回可用大纲时请用户确认建议大纲和搜索建议。研究型与综合长篇文种（调研报告、政策研究、产业研究、综合性总结与汇报材料），在大纲或素材确认环节一并给出三行写作定位——读者是谁、读者读完要获得什么、哪些内容分别以正文/表格/清单呈现。
4. 需要搜索时，将大纲搜索建议或用户需求转化为深知搜索方案并等待用户确认；素材库已命中的用户材料优先于搜索素材。
5. 执行深知搜索并整理素材；判断文体结构和段落功能（必要时参考 `reference/standards/99_expressions.md`）；按 `reference/material_usage_guidance.md` 判断材料用途和风险。
6. 生成内部正文草稿；正文须落实已生效的写作偏好。
7. 生成最终 `.docx`（用户要求红头时再生成红头版本）。
8. **如果本次执行过搜索**，用溯源 JSON 生成产出物 HTML（`XXX.html`，三页）。
9. dsh 交付：产物位于会话工作区 `dknowc-output/${DSH_SESSION_ID:0:8}/official-docs/output/`（Word 与产出物 HTML），dsh 以工作区为文件视图、访达也可直达，直接向用户展示脚本实际打印的路径即可，无需交付复制。
10. 向用户交付 `.docx`（如有）与产出物 HTML 路径；说明 HTML 的正文页即正式内容、另两页为溯源与知识专库。

### 路径 B：非公文（未命中开关 A）

1. 同路径 A 的 1-6 步准备正文。
2. **执行过搜索**：生成产出物 HTML（`XXX.html`，三页），交付并附一句话询问是否另出 Word。用户要，再用同一份正文生成 `.docx`。
3. **未执行搜索**：按原流程处理（本方案不改变此类任务的现状）。
4. dsh 交付：规则同路径 A 第 9 步（产物已在会话工作区，直接展示路径）。

不得在大纲/素材确认前向用户发送正文初稿、正文全文、Markdown 文件链接或中间文件路径。需要用户审阅时，先交付产物，再请用户基于产物提修改意见。

如果用户只说"写一份""起草""生成""整理成""润色""改写"等正式写作任务，同样先按两个开关判定交付形态；不要把"未明确要求 Word"理解为需要聊天正文交付。
